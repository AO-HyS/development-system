# Governed execution of the whole feature

Keep the selected parent; new sessions default to Sol High. Apply this recipe
once to the authorized feature, including backend and other nonvisual work.
The parent keeps technical judgment, integration and acceptance. Jev evaluates
explicit obligations; the runtime enforces current evidence and permits.

## Recover the complete contract

Read the spec and every linked authorized ticket. Retrieve linked content; do
not ask the user to recite it. Read the applicable AGENTS and relevant canonical
docs. Preserve accepted decisions and authorization from the current instruction
and sources. Missing ticket/rule content stays unresolved. See
[spec and ticket fields](spec-ticket-contract.md). For legacy definitions assign
stable criterion IDs grounded in their existing requirements and retain the
mapping; this does not authorize changing their behavior.

Before activation prepare a contract with `id`, exact `root`, Git `baseSha`,
`endpoint`, retained `authorization`, `sources: [{id,path,kind}]`,
`tickets: [{id,dependsOn}]`, `criteria: [{id,ticketId,requirement,evidenceRequired}]`
and actual `capacity: {total,providers}`. Every ticket has criteria. References
are repository-relative; the runtime computes hashes. Keep private execution
state outside product source. Never send credentials or whole transcripts.

Use `governance-hooks-audit` to inspect installation. Host trust and operational
capabilities must also be verified. A copied hook or requested model is not
proof. Do not activate a required unsupported route as if it were enforced.
Resolve the absolute installed path once:
`.codex/development-system/governance-runtime/cli.mjs` under the actual HOME.
Governed control commands use a literal absolute path, without shell wrappers,
variable expansion, redirects, command substitution or appended commands.
The coordinator's command environment must actually reach the pinned Jev API.
Without permitted network access, classification remains unavailable and no
permit is issued. Hook trust and network availability are distinct requirements.

## Activate and prepare each action

The portable CLI is `node /absolute/.../governance-runtime/cli.mjs`.
`begin --input /absolute/contract.json --json` binds the observed host session
and model to the contract. An environment variable or supplied JSON identity
alone is insufficient. Existing unfinished bindings cannot be replaced.
`status --json` reports the current run, pending work and capability gaps.

Each boundary proposal names its phase and action, objective, criterion/source
references, actor/attempt, read/write sets, dependencies, selected route,
exact tool and input, relevant evidence references and bounded assertions.
Assertions are not observed facts. Submit it with `classify --input ... --json`;
use `--input-json '<single-line JSON>'` to prepare new proposals without an
ungated file write. Never supply a judgment or success receipt yourself.

Control boundaries such as `intake-review` and the completed `*-return` actions
use `toolName: "governance"`, `toolInput: {}` and `attemptId: null`. They classify
readiness or reconcile an observed return; they do not execute a host tool and
cannot be prepared as one. After a passing intake boundary, advance to research.
Actual dispatch and tool actions use their exact tool input and a unique attempt.

During any active phase, `inspect` permits a coordinator's exact bounded
`cat`, `pwd`, `ls` or `rg` read with an empty write set. Classify and prepare it
like other actual tools. Inspection and research gather information; they do
not require their own future results before starting. Unsupported shell forms
remain unavailable, even when a similar command would be read-only.

Jev returns explicit satisfied/violated/insufficient-evidence obligations. A
missing, malformed or unavailable response supplies no permit. Resolve the
specific missing fact or change the proposal, then classify the new boundary.
Do not retry unchanged state or turn a parent rationale into a passing answer.

`prepare --boundary ID --input ... --json` binds a passing current judgment to
`{actorId,attemptId,toolName,toolInput}`. The host consumes that permit once for
the exact invocation. Changed files, source rules, dependencies, model, scope
or arguments require a new applicable judgment. Known conflicts and missing
dependencies block even when Jev says yes.

## Follow the dependency-ready workflow

| Boundary | Responsible model | What must be established |
| --- | --- | --- |
| Initial localization | Sol/current parent | Complete contract, rules and unknowns |
| Research dispatch/return | Fast read-only profile | Correct sources/tools and concise usable evidence |
| Plan authoring | Astra XHigh | Decisions, coherent files, dependencies, ownership and verification |
| Plan review | Different fresh Astra XHigh | Coverage, failure modes, feasibility and omissions |
| Writer dispatch/return | Flash High for settled packets | Current route, context, disjoint ownership, returned scope and rule/doc consistency |
| Integration/correction | Parent; Astra for unresolved decisions | Compatible outputs, findings resolved on the current candidate |
| Deep review | Independent Astra XHigh | Correctness, security and other affected risks; criterion coverage |
| Verification/closure | Capable verifier plus parent judgment | Actual current behavior, every ticket, review findings and authorized endpoint |

Jev participates before and after the plan review and at every dispatch,
return, correction and closure boundary. Authoring/dispatch questions ask about
readiness; returned-work questions ask about completed evidence. A plan review
receives the requirements, plan, rules and source evidence in a fresh context,
without the author's conversation. Different actor IDs alone do not prove
independence; require observed separate execution and fresh context.

Fast research is a replaceable capability. The native default is Luna High,
with Flash or another permitted profile selected explicitly when supported by
observed availability. Planning and independent review use Astra XHigh. Exact
writing defaults to Flash High. A bounded consequential decision may receive
an explicit Astra packet. No silent fallback; actual identity stays distinct
from requested settings. Browser/vision needs real host capability.

Give each writer [the exact packet](execution-contract.md). Start all useful
eligible disjoint packets within actual host and provider capacity. Serialize
overlapping files and dependency chains. Separate product paths do not isolate
a shared provider database. Receive completion events and inspect actual output;
never equate process exit with accepted behavior. External process adapters
govern launch, lifetime and integration; their receipts do not certify every
internal provider tool. Native writable descendants require proven identity.

Dispatch uses the exact absolute installed CLI `execute --input-json` command.
Its descriptor contains `attemptId`, optional `packetPath` in the hashed read
set, and an absolute isolated `candidateRoot` for a writer. The stored route
determines the executable/model/effort. Prepare each dependent writer candidate
from the current integrated inputs, including applicable uncommitted changes.
The adapter verifies those bytes and records its baseline before launch; only
the new delta is attributed to that writer. It does not mistake earlier sibling
changes for a new worker's edits. Integration remains an explicit parent action.

## Reconcile, correct and close

Use `advance --input ... --json` for the next evidenced phase. No forward skips;
corrections rewind to affected work and invalidate affected evidence. Reuse
unaffected evidence and independent progress. Reviewers and verifiers return
evidence through their registered observed executions; ordinary commands
printing a claimed pass cannot satisfy criteria. Every check binds its real
command, result, candidate and producer. The parent still judges whether the
observation proves the intended behavior.

Jev receives complete selected canonical sources and bounded actual returned
text, plans, findings and changed Git hunks with four context lines. Hunk evidence
is explicitly cumulative against the candidate's Git HEAD. Large unchanged
references may carry metadata only; this never claims their contents were read.
Each selected source and the aggregate request are capped at 64 KiB. Oversize
or unavailable required context produces insufficient evidence. Split work into
coherent smaller packets or supply explicit canonical source shards; do not
silently truncate or omit an obligation to obtain a pass.

Machine check evidence uses the local `verifier` route with provider `local`,
model `deterministic-check`, reasoning `null` and capability `exact-check`.
Its execution descriptor includes `check: {executable, argv}` with a canonical
absolute executable and the approved script/config in the hashed read set.
Only the observed command exit can produce its result. Astra's interpretation
and printed success text cannot replace an actual check. A workflow needing
an unsupported browser or provider evidence adapter retains that explicit gap.

For visible behavior use the approved design, actual affected flow and capable
independent critique before final media. Pure backend work uses API/data/job
evidence appropriate to the requirement. Static checks and screenshots answer
different questions. Do not add unnecessary visual stages or mirror tests.

`close --input ... --json` can record accepted, blocked or interrupted outcomes.
Accepted requires current criterion evidence for every ticket, independent
plan and final review, no gating findings or live/recovery ownership, a passing
closure judgment and the authorized endpoint. The Stop hook requests bounded
continuation for missing work; exhausting continuation is blocked, never success.
Honor user interruption; retain ownership until actual termination is observed.
An uncertain provider/capability or missing termination remains an explicit gap.

Finish with behavior delivered, actual evidence, deployment scope and material
limitations. Do not claim host enforcement, runtime identity or production
acceptance from installation hashes, requested flags or synthetic fixtures.
