# Design direction

Carry the method here; keep each product's choices in its own brief. The user
need not supply an article, remember skill names, or retell earlier decisions.
Use `coding-orchestration` when assigning design, critique or Computer Use work.
For provenance or extension, read [sources.md](references/sources.md). Ordinary
use is self-contained and needs no web lookup.

## Recover and classify the current decision

Read the supplied brief/spec first. Otherwise follow the project's design-context
pointer, or search its planning/spec directories for the affected surface. Load
Impeccable context once at the actual app. A missing discovered surface brief
does not mean no brief exists. Use [brief.md](references/brief.md) to record and
hand off choices.

Classify every recovered statement as a user-confirmed constraint, a product fact
verified from current evidence, or an agent proposal. Never promote a proposal by
repetition. Separate identity decisions—brand, palette, type and imagery
character—from composition, hierarchy and interaction. Preserving the palette
preserves identity; it does not freeze layout, density, grouping or panel behavior.

Continue from the recorded phase: unresolved exploration, refinement of a
selected direction, or implementation of an approved one. Current user
corrections replace older assumptions and remain literal. Mark obsolete boards
as superseded and keep one current decision. Ask only about choices that change
the next proposal. Use `grill-with-docs` once for functional and visual questions
and reuse equivalent answers by decision key. An approved direction or explicit
continuation satisfies downstream confirmation prompts, including Impeccable's
exploration probe. Small styling fixes stay in Impeccable's refinement workflow.

## Explore, then commit

For an open surface inside an existing identity, load Impeccable at the actual
surface and use its current matching procedure. Derive and record candidate
directions before running `concept-seed`; record the chosen seed before rendering
Impeccable's decision page. Preserve evidence in this order:
`candidates → concept-seed → Impeccable decision page → selection`. That page is
the only runtime comparison and selection surface. Do not build another grid,
blind comparator or choice page in `design-direction` or `grill-with-docs`.
Retain Impeccable's own
branches for refinement, a new surface and a new identity. A previously approved
direction continues from its current phase.

Each candidate states an experience thesis, visible composition/hierarchy/
interaction differences, one expressive opportunity coherent with the product,
and one concrete risk or compromise. Keep factual data, tasks, states and finish
level equal. Color swaps, renamed cards or moved tabs alone are not distinct
directions. When the user asks for three, deliver exactly three useful
alternatives; otherwise choose the smallest count that exposes the decision.

Introduce retrievable visual references before asking for abstract taste. The
questionnaire may show those images beside the questions that they clarify;
Impeccable's decision page still owns direction comparison and selection. State
what each reference contributes: density, typography, composition, rhythm,
imagery or interaction. Treat references as a baseline or moodboard, not a
layout to copy.
Preserve reactions literally: “más atrevido” does not imply more color, larger
imagery or more effects; “más limpio” does not erase personality.

Use Impeccable's matching playbook and the project's comp/code preference. Image
generation can express composition or supply assets when their medium matters.
Use an executable prototype for interaction or motion. A generated still cannot
prove tokens, breakpoint behavior or a working transition.

If proposals converge on one generic pattern, change the hypothesis with a
contrasting reference or optional external seed. Product truth and confirmed
constraints remain fixed. If the user rejects every proposal, record the shared
failure and correction, then use Impeccable's steer or re-roll path to generate
revised candidates without coercing a selection.

## Critique without inherited justification

Give the independent visual-capable critic current screenshots, the user task and
context, confirmed constraints, the selected direction when one exists, and each
visual reference with its function. Exclude implementer rationale, self-review,
code effort and earlier critic prose. Require separate judgments for constraint
conformity and compositional quality against the reference level. A score may
support a reasoned judgment; it never replaces visible criteria or triggers an
unbounded loop.

When applying the article's numerical example, keep the orchestrator's target out
of the critic prompt. Run one or two initial critique/correction passes and test
whether named gaps are converging. Continue only for concrete unresolved gaps;
when the same hypothesis stalls, change it instead of repeating the loop.
“Ready to compare” and “no defects found in this scope” never mean that the user
approved a direction.

## Refine and transfer

After the user chooses, refine only that direction. Preserve its distinguishing
composition and interaction, subtract elements that compete with the primary
task, and demonstrate relevant interaction in an executable prototype. Extend to
the necessary pages, sizes and states only after selection. A static image cannot
prove motion; opening a comparison page on a phone cannot prove product mobile
adaptation.

Compare the same representative tasks and states across required device classes.
Decide how hierarchy, density and context adapt, including constrained and wide
layouts when relevant. Record tokens from the product, explicit open/closed
behavior, and preservation of navigation, focus and task state. Use the brief's
reference status to distinguish exploration, approved composition, superseded
reference and verified implementation.

`design-quality` owns independent visual-capable critique and `evidence-capture`
owns the final walkthrough. Resolve specific gaps in a batch and confirm affected
states. A score is supporting evidence, not a retry trigger. Capture final
evidence only after the reviewed candidate is ready.

At handoff, use [handoff.md](references/handoff.md) to put the current decision,
viewable approved images and slice-specific acceptance in the spec, tickets and
worker packet. Reuse the project's design-context pointer. Check actual
attachments before diagnosing missing images; a document path does not prove a
separate upload exists. A copied skill does not prove discovery or influence.

Done means a fresh model can identify the selected direction, what may change,
which references govern and how the requested slice will be accepted. Continue
to specs, tickets or implementation when authorized, without another ceremony.
