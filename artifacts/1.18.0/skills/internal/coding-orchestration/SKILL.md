# Coding orchestration

Optimize **rápido → bien → barato**: elapsed time to the complete usable result,
including corrections and authorized delivery. Preserve requested behavior,
data boundaries and permissions while shortening the critical path.

## Session selection and role ownership

The starting conversation model remains the orchestrator. It chooses available
workers within the user's provider, quota and capability constraints. Installed
rosters and native TOMLs are recommendations, not observed runtime identity or
an enforced provider chain. Consult the roster only when choosing a worker and
use host capabilities to verify the assignment. Design, critique and Computer
Use need actual vision or browser access. A restricted family stays restricted
for every descendant; in a SWE-only experiment, all descendants stay SWE.
Report a missing capability instead of silently substituting an excluded family.

The parent owns the requested result, architecture, integration, conflicts,
verification and delivery. Reuse the existing spec and current task record.
Keep observable completion and the authorized endpoint explicit; a worker's
diff, first implementation or passing lint does not close remaining criteria.

## Execute with useful context

Use tools directly for deterministic work and batch independent reads. Delegate
when independent work shortens delivery or needed independent judgment improves
the result. Use native host agents when available. Keep one writer per surface;
concurrent writes need disjoint ownership and parent-owned integration.

A worker receives root/revision, owned surface, required behavior, relevant
source/asset pointers, constraints, focused checks and expected output. Include
known failures and the next action when resuming. State that routing is settled
and other workers' edits must be preserved. Load only task-specific references;
inherit full history only when a concrete dependency needs it. Challenge an
incorrect plan with evidence rather than implementing its false assumptions.

Receive completion events; reuse a worker for a focused correction. Verify
termination before transferring write ownership. A productive worker is not a
failure merely because several minutes passed. On a failure, identify what
must change before retrying; repeating an unchanged attempt is not recovery.

For host-specific CLI dispatch or provider failure handling, read
[host-dispatch.md](references/host-dispatch.md). For interrupted work or a
multi-ticket run needing explicit recovery/ownership tracking, read
[execution-continuity.md](references/execution-continuity.md). Ordinary bounded
work needs neither a separate planner nor another tracker. Use an explicit
work graph when dependencies or conflicting ownership need one; a pure plan
never grants authority or starts workers.

## Verify the claimed behavior

Choose the quickest adequate existing check, runtime probe or focused test for
the affected contract, plus required repository gates. New tests are justified
by a named failure they catch and help correct. Lint, React Doctor, runtime
checks and reviewers answer different questions; a tool stack is not a checklist.
Preserve check exit codes. Reuse checks while candidate, environment and inputs
remain applicable; repeat or broaden only for relevant changes, failures,
required gates or unresolved concerns. Never bypass required hooks or CI.

The parent reviews ordinary work against the objective and integrated diff.
Request independent review for observed complex risk or when the user asks.
Resolve material findings, verify affected corrections and continue toward
delivery. Review responsibilities do not each require a separate conversation.
A timed-out reviewer cannot turn an unresolved blocker into a passing result.

## Visual acceptance and evidence

For approved visual implementation, `design-direction` owns the handoff of
retrievable selected images and slice-specific criteria. Compare a representative
screen early when establishing a shared visual language. Check role, organization
and useful data before the main verification pass.

When visual quality is part of acceptance, `design-quality` owns Impeccable and
independent visual-capable critique. Reuse that review, correct material findings,
then use `evidence-capture` for the requested final media. Working screenshots
may support diagnosis before final acceptance. Load only the relevant design or
capture branch; backend-only work does not need a visual workflow.

Use the host's authorized browser mechanism. One driver owns a session; stable
capture steps use deterministic tools rather than a model inference per click.
A delegated neutral runner receives its bounded authorized execution plan, not
the private rubric. Host validation of origins, actions and write authority
remains separate; consult `evidence-capture` for those mechanics when needed.

## Finish

Continue until the requested behavior is implemented, relevant validation and
corrections are complete, and the authorized delivery endpoint is reached.
Report the candidate, usable links, checks, unresolved gaps and actual release
state. Separate source, local runtime, PR, Preview, production and acceptance.
If blocked, name the concrete dependency and complete independent work. Record
observed models or usage when reporting a run; labels and copied files alone
prove neither model identity nor live influence. An unaccepted visual attempt
has attempt time, not a measured time to accepted delivery.
